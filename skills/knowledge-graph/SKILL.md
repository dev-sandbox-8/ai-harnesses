# Knowledge Graph Skill

Generate a grounded, hallucination-resistant knowledge base for the target repository.

## Usage

```
/knowledge-graph [path]
```

- `path` — optional target directory. Defaults to the current working directory.
- If `path` is omitted, operate on `cwd`.
- If the target is not a git repo, warn and continue.

## Pre-flight Checks

1. If `AGENTS.md` exists at the target root, read it before modifying anything.
2. If `Knowledge/KNOWLEDGE_GRAPH.md` exists, read it and treat it as the current graph to update, not replace.
3. If `START_HERE.md` exists, read it and preserve any manually written sections.
4. If `Knowledge/` directory exists, reuse its tier subdirectories (`Source of Truth`, `meetings`, `archive`, etc.) where present. Create missing ones.

## Step 1: Scan and Classify the Repository

Recursively enumerate all files in the target directory, excluding:
- `.git/`
- `node_modules/`
- `__pycache__/`
- `.venv/`, `venv/`
- `dist/`, `build/`, `target/`
- `.next/`, `.output/`
- `.DS_Store`
- Any file > 1 MB

### What NOT to put in the knowledge base
- Sensitive credentials, tokens, or keys
- Content that duplicates the source code (the AI can read the source directly)
- Opinions or preferences that haven't been agreed on by the team
- Anything you're not confident is currently true

Classify every discovered file into one of four tiers:

### Tier 1 — Source of Truth (authoritative, read-only for AI)
- Leadership docs, ADRs, architecture decision records, scorecards, policy docs.
- Typical filenames: `README.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, `DECISIONS.md`, `ADR/*.md`, `docs/architecture/*.md`.
- README files at the repo root or in top-level directories count as Tier 1 if they describe system behavior or team conventions.

### Tier 2 — Core Knowledge (technical textbook)
- API docs, component docs, data models, runbooks, technical specs.
- Typical locations: `docs/`, `Knowledge/` (existing files not in Tier 1), `specs/`, `references/`.
- Well-structured markdown explaining "how X works."

### Tier 3 — Working Documents (useful but not authoritative)
- Sprint plans, meeting notes, generated reports, changelogs, todo lists, PR descriptions, issue templates.
- Typical locations: `Planning/`, `meetings/`, `changelogs/`, `.github/ISSUE_TEMPLATE/`.
- Any file with date-stamped naming (`2024-01-15-*.md`, `Sprint_1/`) is Tier 3 by default.

### Tier 4 — Archive (non-authoritative reference)
- Old docs, deprecated guides, legacy migration docs.
- Typical locations: `archive/`, `deprecated/`, `old/`, `legacy/`.
- Any file older than 12 months that has not been modified is Tier 4.

## Step 2: Analyze Code Structure

For every code file discovered, extract:
- Language (by extension)
- Primary module / package / namespace
- Key exported classes, interfaces, functions, and constants (names only)
- Imports / requires / dependencies (module names, not full paths)
- Configuration files and their keys (`package.json` dependencies, `pyproject.toml` sections, `.env.example` keys)

Supported languages and file types:
- TypeScript, JavaScript, Python, Go, Rust, Java, Ruby, YAML, JSON, TOML
- Dockerfile, SQL, Shell
- Framework-specific: `.podspec`, `Podfile`, `.modulemap`, `Fastfile`, `Package.swift`

**Traceability rule:** Every fact in the knowledge base must be traceable to a real file analyzed during this run. Never invent APIs, config keys, or module names.

Do not inline full source. Store only structural metadata.

## Step 3: Build the Document Map (Knowledge Graph)

Create or update `Knowledge/KNOWLEDGE_GRAPH.md` at the repo root.

The file must contain exactly these sections in this order:

### Header
```markdown
# Knowledge Graph
Auto-generated by the knowledge-graph skill. Last updated: YYYY-MM-DD.
Repository: <repo-name>
```

### Document Hierarchy
A table or bullet list grouped by tier:

```markdown
## Document Hierarchy

### Tier 1 — Source of Truth
- `README.md` — Project overview and getting started guide.
- `docs/adr/001-use-postgres.md` — Decision to use PostgreSQL for primary storage.

### Tier 2 — Core Knowledge
- `docs/api.md` — REST API reference for v2 endpoints.
- `Knowledge/01_auth_service.md` — Authentication service internals.

### Tier 3 — Working Documents
- `Planning/Sprint_12.md` — Sprint 12 plan and velocity targets.
- `meetings/2024-03-15-standup.md` — Daily standup notes.

### Tier 4 — Archive
- `archive/migration-v1.md` — Legacy migration guide (deprecated).
```

One-line description per file. Alphabetize within each tier.

### Concept Clusters
Group files by conceptual topic. A single file may appear in multiple clusters.

```markdown
## Concept Clusters

### Authentication
- `docs/adr/001-use-postgres.md` (Tier 1)
- `Knowledge/01_auth_service.md` (Tier 2)
- `src/auth/middleware.ts` (code)

### Data Storage
- `docs/adr/001-use-postgres.md` (Tier 1)
- `docs/api.md` (Tier 2)
- `src/db/schema.ts` (code)
```

### Code Map
Summarize code structure by module:

```markdown
## Code Map

### src/auth/
- `middleware.ts` — Express middleware for JWT validation. Imports: `jsonwebtoken`, `../config`.
- `routes.ts` — Auth route definitions. Exports: `router`. Imports: `middleware.ts`.

### src/db/
- `schema.ts` — Prisma schema definitions. Exports: `PrismaClient`.
```

Keep descriptions to one line. List imports only if they reveal coupling or shared modules.

### Evidence Trails
Connect decisions to their authoritative source files:

```markdown
## Evidence Trails

- **"We use PostgreSQL"** → `docs/adr/001-use-postgres.md:1`
- **"JWT tokens expire after 15 minutes"** → `Knowledge/01_auth_service.md:12`
```

Extract trails by scanning Tier 1 and Tier 2 markdown files for declarative statements (lines starting with "We ", "The ", "All ", or containing "must", "should", "always").

### Source of Truth
List every file referenced or analyzed during this skill run so facts can be traced back:

```markdown
## Source of Truth

This knowledge base was generated from direct analysis of:
- `README.md`
- `Project Structure.md`
- `docs/architecture/*.md`
- `src/auth/middleware.ts`
- `package.json`
```

If no source files were analyzed (e.g., only existing docs were reorganized), omit this section.

### Revision History
Track changes to the knowledge base itself:

```markdown
## Revision History

### YYYY-MM-DD — Initial Build
**What was added:** First three-layer knowledge base for the project.
**Trigger:** Skill run on fresh repository.
**Files created:** START_HERE.md, Knowledge/KNOWLEDGE_GRAPH.md, AGENTS.md, Knowledge/Source of Truth/*.md

### YYYY-MM-DD — Dependency & Architecture Update
**Problem solved:** AI agents lacked understanding of compile-time relationships between frameworks.
**What was added/improved:**
| File | Changes |
|---|---|
| `Knowledge/Source of Truth/00_project_context.md` | Added: compile-time dependency graph, module map table, public API |
```

If the graph was just created with no prior history, include only the "Initial Build" entry. If updating an existing graph, preserve prior entries and append a new one.

### Navigation Paths
Provide quick routes for common tasks:

```markdown
## Navigation Paths

### Onboarding a new engineer
1. `START_HERE.md`
2. `README.md`
3. `docs/adr/001-use-postgres.md`
4. `Knowledge/01_auth_service.md`

### Debugging authentication failures
1. `Knowledge/01_auth_service.md`
2. `src/auth/middleware.ts`
3. `src/auth/routes.ts`
4. `meetings/2024-03-15-standup.md`

### Reviewing architecture decisions
1. `docs/adr/*.md`
2. `README.md`
3. `docs/architecture/*.md`
```

## Step 4: Create or Update START_HERE.md

Path: `<repo-root>/START_HERE.md`

If the file already exists, append or update only the missing sections. Do not delete user-written content.

Required sections:

```markdown
# START_HERE.md

## What is this project?
<2-3 sentences describing the project purpose, derived from README or Tier 1 docs.>

## Who is on the team?
<If OWNERS, CODEOWNERS, or team references exist, list them. Otherwise write: "See CODEOWNERS or team directory.">

## What are we building?
<High-level feature summary derived from README and Tier 2 docs.>

## Where are the credentials?
<Point to `.env.example`, secrets manager docs, or Tier 1 security docs. If none found, write: "No credential documentation found. Check `.env.example` or ask your team lead.">

## How do I run this?
<Derive from README, package.json scripts, Makefile, Dockerfile, or CI config.>

## Knowledge Graph
- `Knowledge/KNOWLEDGE_GRAPH.md` — The full document map.
- Tier 1 files are authoritative. Tier 4 is reference-only.

## Rules for AI Agents
1. Read `Knowledge/KNOWLEDGE_GRAPH.md` before answering questions.
2. Cite sources as `file:line`.
3. Tier 1 overrides Tier 2, which overrides Tier 3.
4. Never speculate. Say "I don't know" when unsure.
```

## Step 5: Create or Update AGENTS.md

Path: `<repo-root>/AGENTS.md`

If the file already exists, merge the rules below with existing content. Do not overwrite user-defined rules.

Required content:

```markdown
# AGENTS.md — Rules for AI Agents

## Session Initialization (MANDATORY)
1. Read `START_HERE.md`
2. Read `Knowledge/KNOWLEDGE_GRAPH.md`
3. Read relevant Tier 1 and Tier 2 files before answering
4. Cite sources as `file:line`
5. Never speculate. Say "I don't know" when unsure.

## Authority Hierarchy
- Tier 1 (Source of Truth) overrides all other tiers.
- Tier 2 (Core Knowledge) overrides Tier 3 and Tier 4.
- Tier 3 (Working Documents) is useful for context but not authoritative.
- Tier 4 (Archive) is reference-only.

## Hard Rules
1. **Never contradict a Tier 1 document in a Tier 2 document.** If they conflict, update Tier 1 through a deliberate decision and note why.
2. **Never duplicate content.** One source per fact. Other files point to it, not repeat it.
3. **Never invent.** Only write facts you can trace to a real file in the repository.
4. **Keep the Knowledge Graph current.** A stale graph produces stale AI answers. Update `KNOWLEDGE_GRAPH.md` whenever you add or rename a knowledge file.
5. **Archive, don't delete.** When docs become outdated, move them to `Knowledge/archive/` and mark them non-authoritative rather than deleting.

## When to update

| Trigger | What to update |
|---|---|
| New framework or module added | Add row to `Knowledge/KNOWLEDGE_GRAPH.md`, create new Tier 2 file |
| Architecture decision made | Add to `Knowledge/Source of Truth/00_project_context.md` |
| New naming or coding convention | Update `Knowledge/Source of Truth/01_coding_conventions.md` |
| New public header annotated | Update `Knowledge/Source of Truth/02_nullability_rules.md` or equivalent |
| Version shipped | Update `Knowledge/Source of Truth/03_release_process.md` and `START_HERE.md` |
| New build script or CI lane added | Update build/release knowledge files |
| New test pattern established | Update testing knowledge files |
| Decision in a meeting | Add a file to `Knowledge/meetings/` |

## Maintenance
- Update `Knowledge/KNOWLEDGE_GRAPH.md` when adding or moving files.
- Re-run this skill monthly to keep the graph fresh.
```

## Step 6: Validation

After generating files, verify:
1. `Knowledge/KNOWLEDGE_GRAPH.md` exists and contains all required sections: Header, Document Hierarchy, Concept Clusters, Code Map, Evidence Trails, Source of Truth, Navigation Paths, and Revision History.
2. `START_HERE.md` exists and contains all six required sections.
3. `AGENTS.md` exists and contains Session Initialization, Authority Hierarchy, and Hard Rules.
4. No Tier 1 file is listed as missing or misclassified.
5. All code files listed in the Code Map actually exist at the referenced path.
6. Every fact in Tier 1 and Tier 2 knowledge files traces to a real source file.

If any validation fails, fix before finishing.

When the skill completes, print a summary:

```

- Tier 1 files: N

- Tier 3 files: N
- Tier 4 files: N

- Concept clusters: N

- Files updated: <list any updated files>
```
